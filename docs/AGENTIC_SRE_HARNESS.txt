MESH AGENTIC SRE WORK HARNESS
=============================

Purpose
-------
This is the living implementation harness for evolving Mesh from a bounded
remediation control plane into a bounded, auditable AI-SRE system. It maps the
work, records active implementation checkpoints, and tracks validation as the
work proceeds.

The core invariant is stable:

  Mesh may become agentic in investigation, hypothesis testing, arbitration,
  and learning. Mesh must remain bounded, policy-gated, operator-steerable, and
  auditable for production mutations.


Current Mesh Architecture Map
-----------------------------
Existing runtime spine:

  IngestService
    -> TriggerService
    -> EvidenceService
    -> ScenarioAnalysisService
    -> DecisionService
    -> EvaluationService
    -> operator gate
    -> OrchestratorService
    -> FeedbackService
    -> learning, vault, Merkle, memory

Important current strengths:

  - Signals are normalized before downstream stages read them.
  - EvidenceService promotes a signal from a lead into an audited evidence pack.
  - ScenarioAnalysisService emits evidence nodes and subdecisions.
  - DecisionService owns the bounded decision vocabulary.
  - EvaluationService enforces policy and quality gates before execution.
  - OrchestratorService owns bounded side effects.
  - FeedbackService records outcomes for learning.
  - AgentMeshService records proposal artifacts but does not own production
    side effects.

Known current limitations:

  - Investigation is mostly implicit in evidence and scenario analysis.
  - Hypothesis generation is deterministic and template-heavy.
  - Agent lanes mostly review or propose after a decision exists.
  - Confidence is partly heuristic and not fully calibrated by learned priors.
  - Parallel read-only evidence gathering is not yet a first-class stage.


Target AI-SRE Architecture
--------------------------
Target runtime spine:

  alert/correlation
    -> context assembly
    -> audited evidence pack
    -> read-only InvestigationService
    -> scenario analysis and memory synthesis
    -> bounded decision
    -> SRE judge and policy evaluation
    -> trust ladder / operator gate
    -> bounded execution or proposal artifact
    -> feedback learning

Target system capabilities:

  - Triage every eligible alert as a lead, not a truth.
  - Build a scoped incident context from telemetry, topology, memory, and recent
    change history.
  - Form multiple hypotheses and test them with read-only probes.
  - Stop investigation when uncertainty is low enough, the probe budget is
    exhausted, or more evidence is unlikely to change the bounded decision.
  - Route specialized agents by signal source and service domain.
  - Reconcile agent disagreement before recommending a bounded action.
  - Learn from feedback without bypassing policy.


Workstream Roadmap
------------------
W0 - Harness and first investigation contract
  Status: completed first slice.
  Goal: add this harness and a conservative deterministic InvestigationService
  stage after EvidenceService and before ScenarioAnalysisService.

W1 - InvestigationService v1
  Goal: add read-only investigation reports with probe results, citations,
  uncertainty, and stop reasons.
  Scope: deterministic built-in probes only.
  Out of scope: LLM-generated probe plans, live shell execution, mutating tools.

W2 - Bayesian decision confidence
  Goal: replace caller-supplied causality confidence and fixed confidence nudges
  with learned, auditable priors from FeedbackService outcomes.

W3 - Agent routing and arbitration
  Goal: route agents by signal source and service scope, then reconcile proposal
  disagreement instead of selecting the first successful attempt.

W4 - Read-only probe registry
  Goal: introduce pluggable read-only tools for Prometheus, logs, traces,
  Kubernetes, Git/deploy metadata, and runbooks.

W5 - SRE eval harness
  Status: in progress.
  Goal: score investigation quality, root-cause accuracy, unsafe-action
  avoidance, and decision stability across synthetic and fixture incidents.


External Agentic-SRE Pattern Notes
----------------------------------
OpenSRE pattern:
  Treat incident response as a scored environment, not only a chatbot or
  workflow. Useful benchmark axes are root-cause accuracy, evidence grounding,
  unsafe-action avoidance, remediation quality, and time-to-useful-decision.

Resolve.ai / agentic ops pattern:
  Separate investigation, diagnosis, and execution. Agents can collect and
  summarize evidence, but production-changing actions remain approval-gated and
  auditable.

Loghub / AIOps corpus pattern:
  Public log corpora are useful for breadth in log anomaly recognition and
  evidence extraction. They are not sufficient alone for full production SRE
  evaluation because they usually lack topology, deploy metadata, policy,
  operator intent, and recovery observations. Mesh should ingest them as
  provenance-rich scenario seeds, then score them separately from full incident
  fixtures.

AIOpsLab pattern:
  A comprehensive AIOps agent benchmark separates the agent interface from the
  service environment, injects faults, generates workloads, exports telemetry,
  and evaluates agents against reproducible scenarios. Mesh should converge on
  the same separation: scenario generation, runtime execution, scoring, and
  reports are distinct layers.

Benchmark design implication:
  Mesh architecture iterations must produce comparable scorecards across a
  stable golden suite and larger generated corpora. A high score requires both
  correct bounded decisions and grounded reasoning artifacts; agentic behavior
  that is not cited, reproducible, and policy-safe should not improve the score.
